# نقشه راه تثبیت تجربه توسعه‌دهنده Karnoweb Task Manager

**نسخه: طرح اولیه مبتنی بر بررسی ZIP مورخ ۱۴۰۵/۰۷/۳۰ (۲۰۲۶-۱۰-۲۲)**  
**مبنای بررسی:** `task-manager.zip`، به‌ویژه `dev/`، `src/`، `docs/` و `tests/`، در مقایسه با `laravel-inventory.zip`.  
**وضعیت کار:** گام صفر (ممیزی و استخراج قرارداد) انجام شده؛ مراحل تغییر کد، بازنویسی اسناد و اجرای تست هنوز آغاز نشده‌اند. **هیچ فایل پکیج حذف یا تغییر نکرده است.**

## تصمیم اصلی

قرار نیست Task Manager کوچک‌تر یا کم‌امکانات‌تر شود؛ قرار است **استفاده از آن قابل‌فهم‌تر** شود. الگوی مرجع Inventory است: نصب کوتاه، شروع پنج‌دقیقه‌ای، Facade گروه‌بندی‌شده، قابلیت‌های اختیاری و سناریوهای انسانی کنار تست‌های اجرایی.

**خط قرمز:** از ساده‌سازی نباید دسترسی ناامن، نشت داده بین Scopeها، حذف نسخه/شناسه عملیات، تغییر مالک وضعیت Workflow، یا وابستگی اجباری به Kanban/Calendar/CRM حاصل شود.

## آنچه اکنون مستند و قابل استناد است

| اسناد سناریو در `docs/TEST-SCENARIOS` | ۲۴۱ (۲۳۶ `TM` و ۵ `E2E`) | جفت‌های PHP/MD در `tests/Scenarios` | نیاز به فهرست سناریوهای انسانی و ردیابی حفظ‌شده |

این اعداد تنها درباره محتویات ZIP بررسی‌شده‌اند. وجود یک تست به‌معنی قبولی آن نیست. محیط بررسی فاقد Composer/vendor و PHPUnit قابل اجرا بود؛ تست پکیج اجرا نشده است.

## معماری/قراردادهای کشف‌شده که باید حفظ شوند

- Facade: `Karnoweb\TaskManager\Facades\TaskManager`، مدیر اصلی: `src/TaskManager.php`.
- `TaskManager::tasks()` یک `TaskService` برمی‌گرداند که مسیرهای موجود `createTodo(CreateTodo)`، `inContext(ExecutionContext)`، `change(MutateTask)` و `findTasks(TaskQuery)` دارد.
- `TaskSession` موجود در `src/TaskSession.php` یک مسیر خوانای `create/get/complete` با Context اختصاصی همان درخواست است.
- `ExecutionContext` دارای `scope`، `actor`، `correlationId` و مجموعه مجوزهاست؛ نقش آن نباید با وضعیت سراسری/ضمنی ناامن جایگزین شود.
- حتی Todo شخصی با موتور وضعیت داخلی `personal` کار می‌کند و به Project، Kanban یا Calendar نیاز ندارد.
- `WorkflowService` تعریف نسخه‌دار را منتشر می‌کند، `PipelineService` نگاشت مراحل را نگه می‌دارد و `InstanceService` وضعیت اجرای واقعی و انتقال‌ها را مدیریت می‌کند؛ Board صاحب وضعیت نیست.
- `SubjectRegistry`/`SubjectHandler` موجودیت خارجی را متصل می‌کنند، بدون انتقال مالکیت داده تجاری آن به پکیج.
- وابستگی‌های اختیاری مانند Provider مسیریابی، گیرنده یادآور و مقصد اعلان از Laravel Container تزریق می‌شوند؛ لازم نیست همه به گزینه Config تبدیل شوند.
- متد `__call()` در `TaskManager` متدهای عمومی `TaskService` را عبور می‌دهد. این رفتار باید صریحاً مستند و برای سازگاری عمومی بازبینی شود؛ حذف عجولانه مجاز نیست.

## مراحل اجرا و معیار پذیرش

### گام ۰ — ممیزی (انجام‌شده در این دور)

**خروجی:** نقشه راه حاضر و نقشه اولین قراردادهای عمومی.  
**اقدام بعدی پیش از تغییر کد:** ثبت inventory همه متدهای عمومی و تفکیک «مخاطب توسعه‌دهنده» از «ابزار داخلی»؛ مشخص‌کردن dependency و نوع خروجی هر گروه سرویس.

**معیار پذیرش:** برای هر عملیات رایج بتوان مسیر واقعی کلاس/متد، ورودی، Context، خروجی، خطا و تست مرجع را پیدا کرد.

### گام ۱ — تثبیت API عمومی و تجربه شروع (اولویت P0)

۱. سه مسیر یادگیری تعریف شود: **Todo شخصی**، **Project و Task**، **Workflow موجودیت خارجی**.
۲. در مسیر Todo، نخست از `tasks()->inContext(context)` و روش‌های DTO موجود استفاده شود؛ API جدید فقط در صورت شکاف ثابت‌شده پیشنهاد شود.
۳. Context از هویت قابل اعتماد پروژه میزبان ساخته شود؛ اطلاعات `actor/scope/capabilities` از درخواست خام کاربر نپذیریم.
۴. شناسه یکتای عملیات و نسخه رکورد با توضیح قابل فهم مستند شوند (Idempotency و optimistic version).
۵. جدول «چه کسی از کدام Facade و Service استفاده کند؟» همراه خروجی‌های واقعی تهیه شود.
۶. در صورت نیاز، تنها facade-helperهای سازگار با نسخه قدیم، با تست سازگاری افزوده شوند؛ هیچ API فعلی حذف نشود.

**معیار پذیرش:** توسعه‌دهنده بتواند بدون ساختن Project یا Workflow، یک Todo بسازد/بخواند/تکمیل کند؛ سپس پروژه و گردش‌کار را با نمونه واقعی پیاده کند؛ همه این مسیرها تست اجرایی داشته باشند.

### گام ۲ — تنظیمات و قراردادهای میزبان (اولویت P0)

۱. برای تمام گزینه‌های موجود در `config/task-manager.php` مقدار پیش‌فرض، اثر عملی و مثال تنظیم ارائه شود.
۲. مشخص شود کدام ویژگی بدون هیچ Provider کار می‌کند، کدام دارای Provider امن پیش‌فرض است و کدام بدون پیاده‌سازی میزبان خطا می‌دهد.
۳. نمونه واقعی اتصال برای `AuthorizationProvider`، `SubjectRegistry`، `EntryRoutingProvider`، `ReminderRecipients` و سیستم اعلان فراهم شود.
۴. از افزودن پرچم‌هایی مانند `workflow.enabled` بدون نیاز واقعی پرهیز شود؛ Core باید ساده باقی بماند.

**معیار پذیرش:** جدول «الزامی / اختیاری / پیش‌فرض / نقطه توسعه / خطای عدم تنظیم» کامل باشد؛ هیچ وابستگی پنهانی برای نصب پایه وجود نداشته باشد.

### گام ۳ — ساخت سناریوهای جامع انسانی (اولویت P1)

**معیار پذیرش:** همه الزامات اصلی PRD و Ticketing یا در یک سناریوی جامع یا در یک تست تخصصی با ردیابی روشن حضور داشته باشند؛ تست جامعی که نوشته می‌شود در PHPUnit اجرا و نتیجه ثبت شود.

### گام ۴ — نوشتن مستندات جدید برای مصرف‌کننده (اولویت P1)

ساختار هدف پیشنهادی (تعداد صفحات به‌جای تعداد پوشه‌ها ملاک نیست):

- `README.md` — معرفی، نصب، نمونه Todo کوتاه، پیوند نقشه راه آموزشی.
- `docs/README.md` — فهرست و سه مسیر مطالعه.
- `docs/01-getting-started/` — نصب، شروع سریع، مدل ذهنی.
- `docs/02-core-concepts/` — Task، Project، Workflow، Pipeline، Stage، Instance، Subject، Case، Board.
- `docs/03-basic-usage/` — Todo، لیست، پروژه، مسئول، زمان‌بندی، یادآور.
- `docs/04-workflow/` — تعریف، نسخه، انتقال، خطا و فرمان ویژه.
- `docs/05-advanced/` — Handoff، SLA، Approval، Automation، گزارش.
- `docs/06-integrations/` — مدل خارجی، Ticketing، CRM، Kanban، Calendar.
- `docs/07-reference/` — Config، API، Context، DTO، Contracts، Exception، Events.
- `docs/08-internals/` — دیتابیس، تراکنش، امنیت، Outbox و معماری توسعه داخلی.
- `tests/Scenarios/Guided/README.md` — فهرست سناریوهای انسانی با پیوند به PHP/MD.

در هر راهنمای عملی: **هدف → حداقل پیش‌نیاز → مسیر دقیق فایل و Namespace → مثال اجرایی → ورودی/خروجی → اثر دیتابیس → خطا و مجوز → تست متناظر**.

**معیار پذیرش:** تمام مثال‌ها از امضاهای واقعی سورس استخراج و با تست DocumentationExamples صحت‌سنجی شوند؛ توسعه‌دهنده برای استفاده روزمره نیازی به خواندن سورس نداشته باشد.

### گام ۵ — پاک‌سازی کنترل‌شده (اولویت P1)

۱. ابتدا فهرست ارجاعات داخلی ساخته شود؛ هیچ فایل مرجعی تا انتقال محتوای یکتایش حذف نشود.
۲. اسناد فازهای تاریخی، گزارش‌های XML/JSON، خروجی Gate و logها از راهنمای عمومی تفکیک شوند. مکان پیشنهادی برای شواهد جاری CI/Artifacts یا release archive است، نه `docs` مصرف‌کننده.
۳. فایل‌های `docs/TEST-SCENARIOS/TM-*.md` فقط پس از نگاشت کامل، اعتبارسنجی سناریوهای جدید و حفظ منبع PRD آرشیو/حذف شوند.
۴. لینک‌های شکسته README و ارجاعات متقاطع اصلاح شوند؛ مرجع API فعلی تا جایگزینی کامل حفظ شود.
۵. `dev/` فعلاً به‌عنوان منبع نیازمندی و تاریخچه **حفظ** شود؛ تصمیم انتقال به آرشیو جداگانه است.

**معیار پذیرش:** هیچ لینک داخلی خراب نماند؛ هیچ نیازمندی بدون مرجع تست نباشد؛ شواهد بازتولید خطاهای گذشته از بین نروند.

### گام ۶ — Gate نهایی، سپس اتصال CRM (اولویت P0 پیش از انتشار)

۱. اجرای همه تست‌های واحد، یکپارچه و سناریویی و ثبت نتیجه واقعی با commit SHA.
۲. اجرای حداقل روی SQLite، PostgreSQL و MySQL/MariaDB مطابق ماتریس پشتیبانی واقعی.
۳. احراز صحت Context/Scope، هم‌زمانی، Worker Retry، After Commit، Idempotency و امنیت Ticketing.
۴. تست نصب مستقل بدون Kanban/Calendar و تست ترکیب‌های اختیاری.
۵. فقط پس از تأیید این Gate، مقایسه دقیق سورس CRM و برنامه Cutover واقعی تهیه شود.

**معیار پذیرش:** خطاهای Critical/High باز وجود نداشته باشند؛ گزارش نتیجه تست و پوشش نیازمندی‌ها کامل شود؛ تصمیم Go/No-Go مستند باشد.

## ترتیب واقعی کار از همین امروز

- **اکنون:** گام صفر تکمیل، قرارداد اولیه و شکاف‌ها استخراج شده‌اند؛ فایل‌های پکیج دست‌نخورده‌اند.
- **اولین تغییر پیشنهادی:** ایجاد `docs/README.md`، `docs/01-getting-started/quick-start.md` و فهرست واقعی Facadeها **بر اساس APIهای موجود**، همراه تست نمونه؛ تا قبل از این کار پاک‌سازی انجام نشود.
- **بعد:** نمودار مفاهیم و راهنماهای Project/Workflow/Subject و سپس سناریوهای GS-01، GS-03، GS-10، GS-11 به‌عنوان نمونه استاندارد سبک سناریو.
- **در پایان:** تکمیل ۲۴ سناریو، نگاشت همه موارد PRD، پاک‌سازی فایل‌ها و Gate تست.

## کارهایی که عمداً الان انجام نمی‌دهیم

- حذف کد، متد عمومی، تست یا Migration؛ بازنام‌گذاری breaking API؛ افزودن Feature flag بدون دلیل؛ قراردادن Context متغیر در Facade سراسری؛ ساخت وابستگی مستقیم به CRM، Department یا Board میزبان؛ ادعای قبولی تست‌های اجرا‌نشده.
