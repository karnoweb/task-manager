# وضعیت اصلاح تجربه استفاده

[فهرست راهنما](README.md). این صفحه قرارداد فعلی و محدودیت‌های باقی‌مانده را توضیح می‌دهد؛ پیشنهادهای قبلی در تاریخچه Git قابل بازیابی‌اند.

| موضوع | وضعیت فعلی | سازگاری و آزمون |
|---|---|---|
| ساخت مستقیم کار پروژه | projects()->createTask(context, projectKey, type, title, operation) پیاده شد؛ خروجی آرایه و نسخه نخست ۱؛ بدون Todo موقت | مسیر قدیمی create/preview/move محفوظ؛ مدیریت و ویرایش پروژه و دسترسی Task هنگام اجرا و بازپخش دوباره بررسی می‌شوند؛ DeveloperExperienceTest و ProjectCreationConcurrencyTest |
| نشست TaskSession | update/reopen/archive/restore/query اضافه شدند؛ واگذاری به سرویس اصلی | سه متد قبلی و TaskResult حفظ شدند؛ زمینه سراسری ایجاد نشده؛ تعارض نسخه و قوانین Workflow برقرارند |
| ساخت زمینه روزمره | context() و inContext() بدون آرگومان، از Resolverهای معتبر و احراز هویت؛ زمینه صریح همچنان معتبر است | ContextFactoryTest و سناریوهای ۱/۱۴؛ شناسه رشته‌ای، شعبه اختیاری و منع مجوز/نشت؛ بدون تغییر Schema یا نگاشت خودکار Scope |
| کشف Facade | @method برای دسترسی‌های واقعی مدیر و مسیرهای TaskService و @mixin افزوده شد | __call، کلید اتصال، نام پارامتر و خروجی‌های قبلی حفظ شدند؛ آزمون Reflection (خواندن امضای واقعی کلاس) و فراخوان واقعی |
| محافظ سفارشی | مجموعه تغییرناپذیر TransitionGuards از Container (سامانه تزریق وابستگی) دریافت می‌شود | آرایه guards سازنده قبلی تقدم دارد؛ نام غایب/مقدار نامعتبر همچنان خطا دارد؛ SubjectHandler و StageLifecycle حفظ شدند |
| تنظیم صفحه | page_size/max_page_size برای query روزمره Task، Instance، Reminder و queries()->tasks فعال شدند | پیش‌فرض ۳۰ و سقف ۱۰۰؛ limit صریح و TaskQuery قرارداد قبلی را نگه می‌دارند؛ آزمون چهار مسیر، مرز و آرگومان نام‌دار |

## محدودیت‌های واقعی باقی‌مانده

- createTask فعلاً همان سطح manager زنجیره انتقال قدیمی را می‌خواهد؛ اجازه ساخت برای member تصمیم سیاستی جدا است، نه باگ. تغییر آن باید آزمون تفکیک مجوز و جلوگیری از انتقال ناخواسته داده داشته باشد.
- حذف limit در حضور آرگومان نام‌دار بعدی، با پیش‌فرض امضای PHP پر می‌شود؛ اندازه صفحه را برای چنین فراخوانی صریح بدهید. [جزئیات](configuration.md).
- list_id هنوز در ساختار داده لازم است؛ برای Task پروژه ممکن است Inbox مالک ایجاد شود، اما Task یا Instance شخصی موقت ساخته نمی‌شود. تغییر این ساختار نیازمند تصمیم مستقل مهاجرت داده است.
- سرویس ساخته‌شده در پردازشگر طولانی‌عمر، اتصال تازه Guard را خودکار نمی‌گیرد؛ مجموعه باید هنگام راه‌اندازی میزبان ثبت شود و callback کاربر قبلی را در خود نگه ندارد.
- اتصال‌های واقعی Ticket/CRM، ارسال اعلان و پایگاه‌داده PostgreSQL باید در محیط مربوط به خودشان تأیید شوند؛ نتیجه SQLite جانشین آن‌ها نیست.

| رفتار فعلی | پیشنهاد دقیق | سازگاری | آزمون ضروری |
|---|---|---|---|
| جمع زمان مراجعه با ۱۰۰هزار رکورد در PostgreSQL پیش‌فرض، یک پرس‌وجوی بیش از ۶۰۸ ثانیه داشت و لغو شد؛ با حافظه ۶۴ مگابایت آزمون کامل موفق شد | ابتدا EXPLAIN زیرپرس‌وجوی visibility گرفته شود؛ اگر پیمایش تکراری تأیید شد، مجموعه مجاز Subjectها با اتصال SQL مناسب و بدون بارگیری تمام شناسه‌ها در PHP بازنویسی شود | امضا و خروجی عمومی ثابت؛ حذف فیلتر میزبان یا تبدیل شمارش مجاز به شمارش خام مجاز نیست | داده ۱۰هزار/۱۰۰هزار، چند نوع Subject، چند قلمرو، لغو دسترسی، برابری count و فهرست، حافظه و زمان واقعی هر سه موتور؛ مقایسه برنامه SQL قبل/بعد |
