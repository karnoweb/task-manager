# پیشنهادهای اصلاح تجربه استفاده

[فهرست راهنما](README.md) · مبنا: [گزارش مرحله دوم](../dev/TaskManager-Stage-2-DX-Review-FA.md)

این فایل پیشنهاد طراحی آینده است؛ هیچ API (رابط برنامه‌نویسی) عمومی یا رفتار اجرایی در این مرحله تغییر نکرده است. نام متد تازه‌ای به‌عنوان قابلیت موجود معرفی نمی‌شود. اولویت P0 یعنی پیش‌نیاز تجربه شروع قابل اعتماد و P1 یعنی بهبود بعدی.

## ۱. ساخت مستقیم Task در Project

**اولویت: P0.** رفتار فعلی: `tasks()->create` کار شخصی می‌سازد؛ مصرف‌کننده برای پروژه باید `previewTaskMove` و سپس `moveTask` را همراه نگاشت وضعیت فراخواند. `ProjectService` متد ساخت مستقیم کار پروژه ندارد. زنجیره چند فرمان مستقل است و شکست مرحله آخر می‌تواند Todo شخصی ایجادشده را باقی بگذارد.

رفتار پیشنهادی: در طراحی بعدی، عملیات ترکیبی ایجاد کار پروژه با استفاده از منطق و کنترل‌های موجود بررسی شود؛ ورودی‌های حداقلی پروژه، نوع کار، عنوان، زمینه معتبر و شناسه عملیات داشته باشد و انتخاب وضعیت اولیه/نگاشت صریح و قابل پیش‌بینی باشد. اتمی‌بودن (همه تغییرات با هم) و نتیجه بازپخش باید پیش از افزودن رابط تعیین شود. این پیشنهاد هنوز نام یا امضای قابل استفاده ندارد.

سازگاری: عملیات فعلی و خروجی آرایه آن‌ها حفظ شوند؛ انتقال کار موجود همچنان مسیر مستقل بماند. سطح دسترسی manage کنونی بدون تصمیم امنیتی پایین نیاید. الگوی Subject، ساختار فرزندها، کلیدهای نمایشی و مالکیت نوشتن حفظ شوند.

آزمون ضروری: موفقیت و برگشت کامل در شکست؛ بازپخش بدون Task/Instance اضافه؛ عدم نشت بین scopeها؛ manager/member/viewer؛ پروژه آرشیوشده؛ تعریف اختصاصی type؛ نگاشت وضعیت نامعتبر؛ کلید نمایشی یکتا؛ رقابت درخواست‌ها؛ حفظ چرخه حیات، رویداد و نمونه main واحد.

## ۲. عملیات TaskSession

**اولویت: P1.** رفتار فعلی: نشست تغییرناپذیر فقط create/get/complete دارد؛ برای reopen، update، archive و query باید به TaskService و DTO (شیء انتقال داده) برگشت. خروجی نشست TaskResult است، اما مسیر آرایه‌ای کلیدهایی مانند public_key دارد.

رفتار پیشنهادی: پس از انتخاب سناریوهای پرتکرار، گسترش نشست با واگذاری به همان مسیرهای change/findTasks بررسی شود. زمینه درخواست، شناسه پایدار عملیات و نسخه مورد انتظار باید حفظ شوند؛ تکمیل Task پروژه همچنان به گردش‌کار هدایت/رد شود. فعلاً مستندات نام و قابلیت اضافی به نشست نسبت نمی‌دهند.

سازگاری: متدهای فعلی و خروجی TaskResult تغییر نکنند؛ متدهای TaskService و DTOها حذف یا بازنام‌گذاری نشوند. هیچ context سراسری در Facade (درگاه ایستای Laravel) ذخیره نشود.

آزمون ضروری: برابری اثر با مسیر DTO؛ جدایی دو نشست و دو کاربر؛ تداخل نسخه؛ بازپخش و لغو مجوز؛ آرشیو/بازیابی؛ محدودیت صفحه؛ خطای workflow_command_required برای پروژه؛ حفظ شروط چرخه حیات و مالکیت نوشتن.

## ۳. تکمیل خودکار Facade

**اولویت: P0.** رفتار فعلی: Facade فایل `src/Facades/TaskManager.php` توضیحات نوعی مشابه Inventory ندارد؛ مدیر اصلی ۴۱ سرویس و عبور پویای __call به TaskService دارد. در Inventory، @method و @mixin کشف سرویس‌ها در ویرایشگر را بهتر می‌کنند.

رفتار پیشنهادی: توضیحات نوعی دقیق از امضاهای واقعی مدیر و مسیرهای عبوری افزوده و با سورس کنترل شوند. روش گروهی مسیر آموزشی اصلی بماند؛ امضاهای ساختگی برای کوتاه‌کردن مثال‌ها افزوده نشوند.

سازگاری: فقط توضیحات فایل PHP تغییر کند؛ نوع خروجی، نام پارامترها، پیش‌فرض‌ها، accessor (کلید اتصال Facade)، نام‌های صریح مدیر و مسیر __call تغییر نکنند. عمومی فنی بودن یک متد به معنی توصیه آموزشی نیست.

آزمون ضروری: تطبیق نام و خروجی ۴۱ دسترسی؛ فراخوان واقعی Facade؛ عبور create/change؛ خطای نام ناشناخته؛ اولویت متد صریح مدیر؛ بررسی ابزار تحلیل نوع/ویرایشگر برای TaskSession و DTOها. در این مرحله مثال‌ها خود Facade فعلی را واقعاً اجرا می‌کنند.

## ۴. ثبت محافظ‌های سفارشی

**اولویت: P0 برای مصرف پیشرفته.** رفتار فعلی: definition.transitions می‌تواند فهرست guards داشته باشد؛ `InstanceService` آرایه callable (تابع قابل فراخوانی) را از سازنده می‌گیرد. Provider اصلی آرایه guards را تزریق نمی‌کند. برای افزودن آن، میزبان به ساخت/اتصال سفارشی سرویس با نگهداری وابستگی‌ها و StageLifecycle (زنجیره کنترل چرخه حیات مرحله) نیاز دارد. نام ثبت‌نشده به guard_unregistered و نتیجه غیر true به guard_veto می‌رسد.

رفتار پیشنهادی: یک نقطه اتصال رسمی برای مجموعه محافظ‌های نام‌دار، با زمان ثبت روشن و بدون بازسازی دستی همه وابستگی‌های InstanceService طراحی شود. این گزارش رابط یا گزینه config (تنظیم) تازه‌ای را موجود فرض نمی‌کند. SubjectHandler::guard برای اعتبارسنجی موجودیت خارجی همچنان قرارداد جداگانه است.

سازگاری: آرگومان guards فعلی سازنده باقی بماند؛ سیاست تقدم اتصال قدیم و جدید مشخص شود. محافظ غایب باید همچنان خطا بدهد؛ حذف قفل، مجوز، SubjectHandler و StageLifecycle برای ثبت محافظ مجاز نیست. محافظ نباید داده تجاری بیرونی را خارج از تراکنش قابل بازگشت تغییر دهد.

آزمون ضروری: محافظ ثبت‌شده موفق/ناموفق؛ نام غایب؛ پرتاب استثنا و برگشت تراکنش؛ حفظ امضای context/instance/payload؛ قلمرو و مجوز؛ رفتار بازپخش؛ حفظ زنجیره پیش‌فرض؛ سازگاری ساخت مستقیم InstanceService با آرایه قبلی؛ زمان ثبت در پردازش‌های طولانی‌عمر.

## ۵. تنظیمات صفحه‌بندی و تفاوت مجوز پیش‌نمایش/اجرا

**اولویت: P1.** page_size/max_page_size فعلاً در امضای سرویس‌ها اعمال نمی‌شوند؛ تغییر config نباید به‌عنوان راه عملی افزایش سقف آموزش داده شود. اگر مصرف واقعی آن‌ها مطلوب است، رفتار default و limit صریح و سقف امنیتی در کار کدی جدا طراحی شود. آزمون حدهای ۰، ۱، ۱۰۰، ۱۰۱، مقدار config سفارشی و فراخوان قدیمی لازم است.

previewTaskMove دسترسی edit پروژه می‌خواهد ولی moveTask manage هم می‌خواهد. فعلاً تفاوت مستند شده است؛ یکسان‌کردن پیام/پیش‌شرط یا تغییر سیاست تنها با تصمیم صریح انجام شود. آزمون member/viewer/manager و لغو مجوز بین پیش‌نمایش و اجرا لازم است؛ دسترسی فعلی نباید ناخواسته گسترش یابد.

## مرز این مرحله

اجرای پیشنهادها انجام نشده است؛ فقط مستندات تازه و آزمون اجرای مستقیم مثال‌ها اضافه شده‌اند. [نتیجه اعتبارسنجی](README.md#نتیجه-اعتبارسنجی) مربوط به رابط فعلی است، نه پیشنهادهای آینده.
