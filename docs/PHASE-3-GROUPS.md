# Conditional group closure — implementation checkpoint

The host owns campaigns. `GroupSourceRegistry` defaults to empty; each registered `GroupSourceProvider` must authorize source access and supply the actual immutable closure revision/cutoff. A caller cannot make up a closed campaign or cutoff to fail business records. `TaskManager.groups()` provides register, immutable policy publication, bounded enrollment, read-only preview/delta, execute, bounded process, current run metadata and authorized paginated reports.

Policy declares protected milestone keys, explicit failure transitions by actual workflow state and a coded reason. Stage names/positions do not grant protection. Terminal records stay unchanged. Verified milestones committed at or before cutoff continue, including valid delegated contracts; waiting sources with no protection and unresolved commit evidence require review. A normal SLA breach alone never substitutes for the campaign's failure policy.

Workflow edges can declare milestone intents. Intents are written with their actual transition/version and roll back with it. `TaskManager.milestones()` verifies only an existing committed intent using the trusted CommitEvidenceProvider, with current subject permission/version. There is no public timestamp setter. PostgreSQL can use actual retained transaction commit evidence; missing tracking, expired evidence or other databases require a trusted host adapter or review. Tests include a controlled trusted ledger and separate real PostgreSQL commit-boundary checks. See PHASE-3-CUTOFF-DECISION.md.

Preview scans permitted group membership using keyset chunks of 250 and scalar SQL evidence/permission subqueries. It returns policy/source revisions, cutoff, counts and a hash of exact member/process versions, visibility and evidence. It writes no run, item, audit or outbox rows. Delta returns a fresh authorized summary. Execute requires the same actor/scope and an unchanged preview; membership/policy/version/evidence changes produce preview_stale. Enrollment is blocked while closing/closed.

Execute hashes and materializes the exact same bounded member rows in one transaction. Each item stores the version that was hashed, rather than re-reading newer versions with a later INSERT SELECT. A process change during or after materialization therefore conflicts at that item and cannot turn an unchanged terminal preview into an unapproved failure. This interleaving has an explicit regression test. Run keys are durable and reject different payloads.

Workers claim bounded items using durable lease tokens/expiry, with real row locks and SKIP LOCKED on PostgreSQL/MySQL. Each item locks/re-authorizes its current source, checks its snapshot version and source campaign evidence, evaluates historical milestones, executes a guarded workflow transition and commits item result plus audit/outbox in one local transaction. A denial or host veto records its own denied/manual-review outcome; other items continue under partial success. A raw SQL exception rolls back that item and preserves its lease for recovery.

Two real workers claim distinct items. A process-termination fixture commits 40 results, commits leases for the remaining 60 and exits before processing them. Recovery cannot steal unexpired leases; after controlled expiry it finishes 60 without repeating the first 40. The tested 100-member case produces exactly 75 failed with campaign_ended, 15 continued (five still delegated), and 10 already terminal. Twelve SLA breaches do not alter those totals.

Reports filter item rows and counts through current instance/subject SQL authorization, use an explicit stable cursor and exclude lease secrets/private host content. An item's operation ID, reason, error and processing timestamp remain durable. Retrying a completed run has no new domain effects. A new run requires a new preview and records its own item/audit outcomes; previously terminal members receive no second business transition.

This is implementation evidence, not a phase-seven release result. Full combined reruns, complete matrix/scale evidence and later UI/host acceptance must be checked separately. No commercial CRM deployment or MySQL validation is inferred from the host fixtures.
